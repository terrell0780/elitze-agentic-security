# ELITZE Agentic Security — Buyer Demo Walkthrough

## Purpose

Demonstrate the core agent-to-MCP control path with attributable evidence. Run this only in an isolated, authorized test environment. Do not point test actions at production systems or third-party MCP servers without explicit authorization.

## Preflight

1. Record repository URL, commit SHA, deployment/environment, operator, and test date.
2. Confirm the environment is isolated and the test agent/MCP server are authorized.
3. Identify the test fixture versus live-connected source. Label each clearly.
4. Confirm logs/evidence are enabled and no production secrets will be exposed.
5. Select one harmless read-only allowed action and one protected action that must be denied.
6. Confirm the protected handler can record whether it was invoked.

If these prerequisites cannot be met, demonstrate only the parts that are safe and label unverified steps. Do not fabricate output.

## Walkthrough

### Step 1 — Discover

Show the source that supplies the agent and MCP server identity. Display the source identifier and observation time.

**Pass:** The record can be traced to its source or is visibly labeled as a test fixture.

### Step 2 — Identify

Show agent identity, tenant, owner if known, environment, MCP server, tools, and credential/workload identity metadata that is safe to disclose.

**Pass:** Known fields are populated from evidence; unknown fields remain unknown.

### Step 3 — Map reachability

Show which tool/resource relationships are observed and which are inferred. Explain the coverage boundary.

**Pass:** The graph does not imply that unobserved resources are unreachable.

### Step 4 — Evaluate policy

Choose the sensitive action and show the applicable policy, subject identity, target tool, and decision rationale.

**Pass:** The policy decision is generated by the actual enforcement path, not a front-end-only display state.

### Step 5 — Allowed action

Run the harmless authorized action.

**Pass:** The tool handler is invoked, the real result is captured, and the decision and result can be correlated.

### Step 6 — Denied action

Attempt the protected action using the same controlled environment.

**Pass:** The policy denies it before execution and the protected handler invocation count remains unchanged. A UI message alone is insufficient evidence.

### Step 7 — Inspect evidence

Show tenant, identity, source, event/decision time, decision, execution result, evidence reference, and integrity properties supported by the implementation.

**Pass:** A reviewer can trace the decision and outcome without relying on mock records.

### Step 8 — Retest

Change one policy in the test environment and repeat the controlled action.

**Pass:** The new decision matches the changed policy and a new attributable evidence record exists.

### Step 9 — Export

Export the actual test results and include the exact commit SHA, environment, prerequisites, command/test identifier, and pass/fail result.

**Pass:** A reviewer can reproduce the same scenario from the instructions.
