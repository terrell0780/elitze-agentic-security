# ELITZE Docker enterprise deployment

ELITZE now ships two Docker deployment layers:

1. **Portable evaluation layer — `compose.yaml`**
   - Runs ELITZE plus a bundled PostgreSQL 18.6 container.
   - Uses a private internal backend network for application-to-database traffic.
   - Runs a migration gate before the application starts.
   - Intended for local evaluation, buyer diligence, development, demos with real infrastructure, and isolated test environments.

2. **Enterprise layer — `docker-compose.enterprise.yml`**
   - Runs ELITZE against a customer-managed PostgreSQL endpoint.
   - Keeps database credentials in a Docker secret mounted at `/run/secrets/database_url`.
   - Exposes ELITZE only on the configured bind address so an enterprise ingress, load balancer, WAF or reverse proxy can sit in front of it.
   - Intended for customer-managed cloud, private cloud, on-premises and controlled enterprise environments.

## Container security baseline

The runtime image uses a multi-stage build and an unprivileged `nextjs` user. The application and migration containers:

- use a read-only root filesystem;
- drop all Linux capabilities;
- enable `no-new-privileges`;
- use bounded PID, CPU and memory limits;
- provide explicit health checks;
- do not mount the Docker daemon socket;
- do not use host networking;
- do not run privileged;
- keep secrets outside image layers and pass the database URL through a secret file;
- make migration completion a prerequisite for application startup.

The bundled database has its own persistent volume and is reachable only from the application's backend network in the portable layer.

Docker recommends rootless mode where the operational environment supports it. ELITZE does not require access to `/var/run/docker.sock`; keep the Docker daemon socket unavailable to application containers.

## Build integrity

The Docker build uses a multi-stage build so build dependencies do not become part of the runtime image. Compose enables SBOM and provenance attestations for builds.

For enterprise registry workflows, retain the published attestations and pair them with the organization’s image admission policy. A registry admission process should reject unsigned, unscanned or stale images according to the buyer's controls.

## Enterprise deployment models

ELITZE can be packaged as:

- **Hosted SaaS** — the existing web deployment model.
- **Customer-managed** — ELITZE container(s) deployed into the customer's AWS, Azure, GCP or private Kubernetes/VM environment, with a customer-managed PostgreSQL service.
- **Private/on-premises** — the same container runtime behind the customer's ingress and network controls, with outbound AI/security integrations restricted to approved endpoints.
- **Controlled/isolated** — customer-provided model gateways and security integrations are used; external connectivity is limited to what the customer's architecture permits.

The AI gateway remains governed by ELITZE policy. `ELITZE_AI_GATEWAY_URL` may point to an authorized OpenAI-compatible enterprise model gateway. No model response is generated by ELITZE when that gateway is not configured.

## Portable evaluation

Generate a local credential file outside git:

```bash
npm run docker:init
docker compose --env-file .env.docker up --build
```

The generated `.env.docker` file is git-ignored. The application should become healthy only after PostgreSQL is healthy and migrations complete.

Check:

```bash
docker compose --env-file .env.docker ps
docker compose --env-file .env.docker logs app
```

## Enterprise deployment

Create a deployment environment that supplies:

```text
ELITZE_DATABASE_URL
NEXT_PUBLIC_SITE_URL
```

Use the customer's secret manager to provide the values to the Compose environment rather than committing them.

Then:

```bash
docker compose --env-file .env.enterprise -f docker-compose.enterprise.yml build --pull
docker compose --env-file .env.enterprise -f docker-compose.enterprise.yml up -d
```

Recommended production topology:

```text
Internet / private ingress
          |
       WAF / LB
          |
     ELITZE :3000
          |
  customer backend policy
          |
 managed PostgreSQL / private DB endpoint
```

The DB endpoint is not published by ELITZE. Apply customer network controls so the container host can reach the database and only the approved external APIs required by the deployment.

## Buyer diligence checks

A qualified buyer should verify, rather than assume:

- image digest and provenance;
- SBOM contents;
- critical/high image vulnerabilities and remediation status;
- base-image update cadence;
- Docker Engine/rootless configuration on the host;
- TLS termination and certificate management;
- PostgreSQL encryption, backups and recovery;
- identity provider configuration;
- egress policy for AI/model and security integrations;
- tenant isolation and authorization tests;
- ELITZE evidence states for observed versus inferred outcomes.

The container layer is a deployment control surface. It does not replace ELITZE's application policy engine, authentication, tenant boundary controls, evidence discipline, or security validation lifecycle.
