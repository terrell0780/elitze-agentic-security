# ELITZE Subprocessor Register — Control Template

This is a schema/control register, not a list of providers. Production providers are added only after contractual, security and privacy review.

| Field | Required |
|---|---|
| Legal entity / provider | Yes |
| Service / function | Yes |
| Processing purpose | Yes |
| Data categories | Yes |
| Customer data involved | Yes |
| Region(s) | Yes |
| Cross-border transfer mechanism | When applicable |
| Security evidence | Yes |
| DPA / contractual basis | Yes |
| Effective date | Yes |
| Review date | Yes |
| Customer notice mechanism | When applicable |
| Objection mechanism | When contractually required |
| Deletion / return capability | Yes |
| Owner | Yes |
| Claim state | Yes |

## Control rules
1. An SDK dependency does not automatically make a provider a subprocessor.
2. A provider used only by a customer-managed integration may require different contractual treatment.
3. Provider location is based on actual service configuration and contract evidence.
4. Security certifications identify scope, issuer and validity period.
5. Production subprocessor changes create a compliance-change event.
6. Stale reviews do not remain silently current.
7. The public register and contractual schedule are reconciled before a provider is treated as approved.

## Evidence
Each register entry links to the executed DPA or contract, provider security evidence, data-flow record, residency/transfer assessment, review record and change/notification history.
